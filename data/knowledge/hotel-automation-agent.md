# Hotel Automation Agent (The Overlook)

## The Project
The Hotel Automation Agent is a public demo Arin built in Python that condenses the kind of AI agent work he did at Wonderful AI into one open-source project. It is an AI back office for email and document automation: it reads a company's incoming emails and PDF attachments, classifies each one, extracts the data with an LLM, checks it against the company's own documents and business rules, and drafts a reply or an action. A human approves every draft before anything is sent (human-in-the-loop). The example client is a fictional mountain hotel, The Overlook, receiving supplier invoices, booking requests, guest questions and suspicious emails, but the same architecture works for any office that handles email from customers, suppliers and contractors. Source code: https://github.com/arinleviti/hotel-automation-agent. Live demo: https://hotel-automation-agent-224143145108.europe-west1.run.app

## What It Does
On the demo emails, the system: checks supplier invoices line by line against contract prices and drafts a correction request when a price is wrong (or an "OK to pay" note when everything matches); handles booking requests by checking room availability and calculating the price with tax in code, asking for missing details such as the number of children, or proposing the three closest free alternative dates when the hotel is fully booked; answers guest questions by searching the hotel's documents with citations, and says "not in the documents" instead of inventing an answer; forwards out-of-scope requests (like a helicopter transfer) to the front desk; and detects prompt injection, for example an email telling "the automated assistant" to skip review and give away a free suite, which is flagged as suspicious and sent to a person.

## LangGraph Architecture
The whole workflow is built with LangGraph as a stateful graph: read_email, classify, decide_route, then one of several branches (invoice, booking, question, or human review), then an approval node and an action node. Each branch is a LangGraph subgraph. Routing between nodes is done by plain Python routing functions, not by the model, so every run is predictable, cheap and testable. Every path ends at a LangGraph interrupt() with a response schema for approve, edit or reject, which implements human-in-the-loop approval. A LangGraph Postgres checkpointer saves each paused run, so a run survives server restarts and resumes when a person decides. Each node has its own retry policy for transient failures and an error handler, so an unreadable PDF or a model timeout becomes a note to the front desk instead of a crash.

## Workflow vs Agent Design
A core design decision is "a workflow, not a team of agents". Invoices and bookings always follow the same steps, so they are deterministic workflows controlled by code. Only one part is truly agentic: the guest-question branch, where Claude decides at each step whether to search again or answer, using tool calling, with a hard limit of four searches enforced in code. This mirrors the node-based, state-machine approach Arin used at Wonderful AI: give the LLM control over the next step only where the path is genuinely open. Another principle is "the model judges, code calculates": the LLM handles language tasks (classification, extracting messy invoice lines, reading dates from free text) using structured outputs, while prices, availability, totals and contract checks are plain Python, and replies containing money or dates are fixed templates filled by code, so a number is never hallucinated.

## RAG Pipeline
The question agent uses agentic RAG over the hotel's documents (PDFs and a Word file). Documents are parsed with Docling, a layout-aware document parser that keeps tables intact, and split with Docling's hybrid chunker along document sections. Arin implemented contextual retrieval: each chunk gets a short Claude-written label describing where it sits in the source (for example "Spa price list, treatments table"), which is embedded together with the chunk text. Embeddings use Voyage AI's voyage-4 model and are stored in PostgreSQL with the pgvector extension and an HNSW index. Search retrieves the top 8 chunks by cosine similarity, then the Voyage rerank-3-lite reranker keeps the best 4. The agent can rephrase its query and search again (query reformulation), and code checks the final answer against the retrieved passages before it reaches a person. Every claim shows its evidence: invoice lines marked as correct, warning or error with reasons, and document passages with their relevance scores.

## Evals, Testing and Observability
Arin built an evaluation suite (evals) that runs the 10 demo emails through the real system three times each with 56 code-based checks: 168 out of 168 checks passed. Unit tests use pytest with fake LLMs, so they run with no API cost. Langfuse provides LLM observability and tracing of every graph node and every model call, including token usage and cost. The prompts are kept as separate Markdown files, versioned in the repository.

## Tech Stack
Python 3.12, LangGraph (graph, subgraphs, interrupt, Postgres checkpointer, retry policies), Claude Haiku 5.5 through the Anthropic SDK (structured outputs and tool use), Docling for PDF and document parsing, Voyage AI embeddings and reranking, PostgreSQL with pgvector (hosted on Neon serverless Postgres), Langfuse for tracing, FastAPI streaming each graph step to the browser with Server-Sent Events (SSE), Pydantic and pydantic-settings, pytest, uv for Python package management, and a React + Vite + TypeScript frontend with an inbox, a live step log and a graph view that lights up the path each run took. One PostgreSQL database holds business data, vectors and LangGraph checkpoints.

## Deployment
The app ships as a single Docker image: Node builds the React frontend and Python serves it together with the FastAPI API. Arin used a CPU-only PyTorch build to keep the image small and downloads Docling's models at build time. It runs on Google Cloud Run (scales to zero) with continuous deployment from GitHub. For the public demo he added safeguards: each visitor gets a private inbox that is deleted after two hours, plus rate limiting and spending caps (30 runs per visitor every two hours, 150 per hour overall). Documented next steps include async graph execution for per-node timeouts, hybrid keyword plus vector search, parallel handling of multi-request emails with LangGraph Send, and an MCP server (Model Context Protocol) exposing the hotel's business tools.
