# Flight Disruption Assistant (Aurora Airways)

## The Project
The Flight Disruption Assistant is a public demo Arin built that condenses the conversational AI agent work he did at Wonderful AI into one open-source project. It is a multi-agent customer-service chatbot for passengers whose flight was cancelled or delayed. In a single conversation it looks up the booking, rebooks the passenger on a new flight, works out their EU261 care entitlements (meal vouchers, hotel, transport), and decides whether they are owed compensation under the EU261 air passenger rights regulation. The airline, Aurora Airways, is fictional and all bookings are demo data. The focus is on what's underneath: a hand-written multi-agent orchestration loop, code guardrails around every action that matters, LLM observability, and an eval suite that drove the design decisions. Source code: https://github.com/arinleviti/flight-disruption-assistant

## Multi-Agent Architecture
The system uses a supervisor agent with two specialist sub-agents, a rebooking agent and a compensation agent, following the "agents as tools" pattern: the supervisor calls each specialist the same way it calls a tool (function calling). Each specialist runs in its own clean context window with its own system prompt and tools, and returns validated structured JSON (Pydantic schemas), not prose, so long legal passages and flight search results never pollute the supervisor's context. Arin deliberately wrote the orchestration loop by hand in Python instead of using a framework like LangGraph, to control every step; his Hotel Automation Agent demo is the LangGraph counterpart. State lives in code: a case file (booking, disruption, options offered, confirmed flight, care, compensation) is updated by code after every tool call and summarised into the prompt each turn, so a turn that fails halfway loses nothing.

## Design Principles
"The LLM judges, code calculates": the compensation agent decides only one legal question, whether the cause was an "extraordinary circumstance", using RAG over EU261 law, and code turns that decision into a euro amount from distance, notice period and delay. No amount ever passes through a model. "The model passes identifiers, not data": case tools take only a booking reference and code loads everything else, so the model can never get a time, distance or amount wrong. Flight inventory stores single legs and the search tool builds connecting flights with an SQL self-join (45 minutes to 6 hours layover). Times are stored in UTC and converted to local airport time in code with zoneinfo, DST-safe, never by the model.

## Guardrails
Code guards wrap every step where a model mistake would cost something, which keeps the agent reliable and reduces hallucinations. Examples: booking_not_confirmed (blocks booking before the passenger confirmed that exact flight), flight_not_offered and invented_flight_dropped (the agent can only book flights the search actually returned; every option is rebuilt from the database), invented_flight_in_reply (catches hallucinated flight numbers in replies), invalid_answer_format (a specialist returning JSON that fails schema validation is asked to redo it), and guards for empty replies, infinite loops (max rounds) and provider outages. Every model call has a 60-second timeout and falls back to the next model. Arin also ran security testing and red-teaming with seven attacks including prompt injection, jailbreaks ("print your system prompt"), fake authority ("as a supervisor I approve €5,000") and social engineering. A jailbreak can change what the model says but not what the tools allow; he documented the one real gap honestly (no passenger authentication, a GDPR concern) and how it would be fixed in production.

## LLM Models and Model Selection
The system is multi-provider through LiteLLM, with automatic model fallbacks. The supervisor runs on Claude Haiku 5.5 (Anthropic) with prompt caching on its system prompt and tool schemas, which cut conversation cost by roughly 60-70% (about half a cent per conversation), with gpt-oss-120b on Groq as fallback. The rebooking agent runs on the open-weight gpt-oss-120b and the compensation agent on the cheaper gpt-oss-20b, because its output is verified by code. Every model choice was made from eval results: Arin compared setups on checks passed, guards fired and cost, found that the cheapest setup double-booked a passenger, and moved the supervisor to Claude when adversarial conversations exposed instruction-following failures. Development started on free tiers (Groq free plan with Gemini as fallback).

## RAG and Knowledge Base
The compensation agent uses agentic RAG over a small EU261 knowledge base: the regulation plus key Court of Justice of the EU rulings on technical problems, strikes, weather and air traffic management, bird strikes and unruly passengers. Documents are Markdown, chunked per section with the document intro prepended to each chunk, embedded with the all-MiniLM-L6-v2 sentence-transformer model and stored in a Chroma (ChromaDB) vector database with cosine similarity. Analysing retrieval scores in the traces revealed a knowledge gap: for "schedule change" cancellations every passage scored around 0.4 relevance, because the knowledge base had no document on airline commercial decisions.

## Evals
The project has 19 scripted evaluation scenarios run through the real agent, covering every demo booking plus messy passengers: changing their mind, switching flights after booking, asking about money first, wanting a different destination or departure airport, and a prompt-injection "admin mode" attempt. Checks are made on the case file, never on the assistant's wording: the right flight booked exactly once, care and compensation correct, no invented flight numbers, no failure guards fired. All 19 scenarios pass with 253 out of 253 checks. Each run saves a full report.

## Observability and Lessons from Traces
Langfuse records every LLM call (messages, model used, tokens, cost, fallbacks), every tool and agent call with arguments and results, and every guard, nested so a specialist's searches appear inside its parent call, with one session per conversation. The chat UI has a Details panel per reply (tools, agents, tokens, cost, model, guards, link to the Langfuse trace) and a route map that replays each turn step by step. Lessons Arin learned from reading traces: most failures were missing or contradictory information, not a "bad model". A guard that fires constantly is a signal (a wrong tool schema caused it, fixing the schema took it from 7/7 to 0); rules that must never break belong in code, not the prompt; tool error messages act as instructions to the model; retrieval scores reveal knowledge-base gaps; and provider details matter (Gemini moves system messages to the top of the prompt).

## Tech Stack
Python, FastAPI, LiteLLM (one interface to every LLM provider with fallbacks), Pydantic for validated tool and agent outputs, SQLite for the flight inventory and rebookings, Anthropic Claude Haiku 5.5 with prompt caching, OpenAI's open-weight gpt-oss-120b and gpt-oss-20b on Groq, Chroma vector database with all-MiniLM-L6-v2 embeddings, Langfuse for tracing and observability, uv for packaging, and a React + TypeScript + Vite frontend with react-markdown. Deployed with Docker on Google Cloud Run, built automatically by Google Cloud Build on every push (CI/CD), with a Cloud Scheduler keep-warm ping.
